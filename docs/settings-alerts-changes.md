# Settings and Alerts audit implementation

This revision contains the web application only. No backend implementation, legal rate schedules, delivery-provider read receipts, or production records were inspected or modified. Existing pricing keys and per-key save requests are preserved.

## Verified data boundaries

- `/api/admin/settings` returns editable setting keys, current string values, fallback strings, type, labels, and hints. The existing POST accepts one `{ key, value }`; the frontend cannot promise atomic updates.
- The job billing contract in `src/api/jobs.ts` and `JobTimeBreakdown.tsx` exposes rate-per-30-minute values and crew/packing setting sources. Displayed crew and packing rate units follow that contract. The underlying billing calculations were not changed.
- `CREW_BILLING_UNIT` is an arbitrary text value in the existing editor. Whether the backend interprets it or uses it only as display text cannot be verified from this repository; the advanced field preserves editing and states that uncertainty.
- The existing editor documents blank `OVERTIME_RATE_PER_30` as inheritance of the relevant crew/packing rate. The redesign displays those effective configured/fallback values and their basis without changing the rule. Actual rounding, minimum duration, and grace application remain backend responsibilities.
- `/api/admin/messages` supplies event/audience/channel, allowed variables, enabled state, and text/HTML settings. Enabled switches persist immediately; edits persist only on Save changes.
- `/api/admin/notifications` provides per-job email/SMS `sent`, `failed`, `pending`, `skipped`, and `disabled` states. It supplies no delivered/read evidence. Display and counts never infer those states.
- `/api/admin/alerts` supplies raw GPS events with driver/device identity but no exact job linkage or confirmed fee. With no range, the endpoint is a latest-50 feed; date-scoped history is available separately.
- The lightweight driver roster supplies active accounts for broadcast selection. Recipient preview counts accounts, explicitly distinguishing these from registered devices/delivery counts.

## Remaining dependencies and business questions

1. **Effect of saved rates on existing jobs:** confirm whether the backend recalculates active/historical jobs on read, saves snapshots, or applies settings only to future calculations. No frontend assertion of historical safety is made.
2. **Billing-unit semantics:** confirm whether `CREW_BILLING_UNIT` is functional. A validated unit selector would require the accepted backend enum/interpretation.
3. **Atomic settings endpoint:** current API only exposes individual writes. Atomic save would require a validated authenticated batch endpoint; current UI faithfully reports per-field outcomes.
4. **Raw GPS alert identity:** raw event rows have no linked job ID. Filtered vehicle monitoring is used; no job association is guessed.
5. **Complete operational attention coverage:** feed windows and available delivery rows cannot establish all missing evidence, stale trackers, unpaid invoices, or driver submissions. Jobs/Overview/Vehicles keep their own validated exceptions; the alert badge is the shared feed count.
6. **Delivery receipts:** delivered/read states require actual provider evidence and are intentionally absent.
